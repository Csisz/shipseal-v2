## Guiding principle

Turn deterministic repository evidence into knowledge, reviewed improvements, truthful verification and one coherent executable future without executing imported code or overstating lifecycle state.

## Completed historical foundation

Historical sprint and schema names remain unchanged even where later planning reused a number.

- **Omega 6–15:** Repository DNA, Repository Intelligence foundations, Mental Model, Living Repository, Repository Universe, actionable Optimization Plan, Optimization Pack apply preparation and session-local rescan verification.
- **Omega 16.0–16.6c:** deterministic JS/TS evidence/context, provider-neutral Deep Intelligence contracts, repository-specific artifacts, reviewed Repository Intelligence PR apply and conservative artifact/statement verification.
- **Omega 17.1–17.3 and later 17.x evolution:** four post-scan chapters, modular/lazy Result Workspace, progressive disclosure, full-bleed Repository Universe, mobile/overlay behavior and truthful proposal-to-verification language.
- **Omega P1:** optional production OpenAI-compatible Deep Intelligence transport behind the provider-neutral boundary, with strict validation and deterministic fallback.
- **Historical Omega 18.1 — account/persistence foundation:** GitHub OAuth account identity, opaque database sessions, private owner-scoped PostgreSQL projects, immutable scan snapshots and versioned verification rows.
- **Later Ω.18.1 / Ω.18.1a — actionable improvement and prepared review:** friction-to-artifact lifecycle, explicit preparation and responsive plan review. This duplicate number is historical and is not retroactively renamed.
- **Ω.18.2 — PR Preview and Apply Hardening:** prepared snapshots, preflight, exact preview/base binding, bounded diffs, explicit confirmation and stage-aware recovery.
- **Deep Intelligence productionization:** bounded redacted provider input, validated future-direction findings, confidence controls and safe fallback.
- **Ω.18.4 — Authoritative Rescan Verification domain:** owner/project/repository-scoped relationship contracts, compatible evidence, statement/graph outcomes and bounded opportunity signals.
- **Post-Ω.18.4 NodeNext hotfix:** explicit server-reachable ESM specifiers and the `typecheck:functions` release gate.

Repository Universe is the primary post-scan signature experience for repository truth. Its WebGL renderer is progressive, and a complete DOM/accessibility path remains mandatory. It is not optional product decoration.

#### Ω.18.5d.4a — Production Product Strategist provider validation repair

#### Ω.18.5d.4b — Exact provider preflight diagnosis and Production-shape repair

Strict preflight now returns a bounded `validationReason` and records the same safe enum in provider operations. The remaining Production-equivalent rejection was `content-safety-absolute-path`: whole-request serialization made a valid repository-relative metadata path such as `src/pages/home/team/page.tsx` match the Unix local-path pattern at `/home/team/`. Server redaction correctly preserved that path, but the field-insensitive second validation misclassified it before provider fetch.

Outbound safety scanning is now field-aware. Repository-relative path/identity fields, system-controlled enums/text, and generated IDs/fingerprints retain their structure and are validated as those categories. Only repository-derived free text—source excerpts, extracted facts, item/outline/responsibility/folder limitations, and known limitations—is scanned for secret and absolute-path content after server redaction. Context, related-file, outline-import, relationship, evidence, responsibility, folder, and framework paths receive repository-relative path validation; context, relationship, and framework evidence references retain closure checks.

The route applies the shared `prepare → ready → strict outbound validation` invariant before provider construction, and the provider defensively revalidates the same finalized request. A synthetic 40-file Product Strategist fixture exercises responsibilities, folders, relationships, framework evidence, structural outlines, selection metadata, server redaction, a 70k–80k token estimate, strict validation, provider envelope parsing, and one mock HTTP fetch. No limits, Product Opportunity behavior, fallback semantics, Future UX, or later-sprint scope changed.

#### Ω.18.5d.4c — Product Strategist context specialization and latency hardening

Implemented on 2026-08-10 by separating Product Strategist execution from general Deep Intelligence while retaining the same provider adapter, credentials, server preparation, redaction, strict preflight, cancellation, retry, response validation and request-fingerprint cache. General Deep Intelligence no longer requests `product-opportunity-analysis`; the focused `product-strategist` profile accepts only `product-opportunity-analysis` plus `structured-output`, requests no general findings and cannot be combined with architecture, routing, risk, documentation, agent-instruction or artifact-statement capabilities.

The deterministic `shipseal.product-strategist-context-policy.v1` selector prioritizes README/product documentation, routes/pages, user-facing components and workflows, API surfaces, persistence/models, account/auth, state, export/share behavior and representative product tests. Agent instructions, CI, build/test configuration, tooling and generic utilities are deprioritized; generated/vendor and sensitive content boundaries are unchanged. Product-facing source is represented by bounded excerpts plus deterministic structural summaries. The browser selection is capped at 18 files and 48,000 characters; the server independently re-applies an 18-file, 35,000 estimated-input-token, 28,000-context-byte and 160,000-request-byte hard profile, pruning unrelated metadata while preserving evidence closure. The configured global policy may make these limits smaller but cannot make the focused profile larger. The hard timeout remains bounded at the smaller of the configured global timeout and 45 seconds, with at most one retry for already-supported transient provider/network categories.

Product analysis now owns an independent UI status, abort controller and single-flight entry point. One focused request fingerprint has at most one active call and accepted Product Intelligence is reused from the session cache; selecting, supporting, replacing or inspecting Future nodes makes no provider request. While analysis is pending, fallback repository improvements are not rendered as strong product directions; they remain available under Other improvements. Success requires validated Product Understanding and three to five accepted user-facing Product Opportunities. Failure, timeout or insufficient accepted opportunities moves explicitly to Repository evidence fallback. Validated opportunities continue through the existing deterministic Product Opportunity adapter and Future Graph dependency mapping; no Ω.18.5e artifact/prompt-pack or Ω.18.5f persistence/apply/rescan/unlock scope was added.

#### Ω.18.5d.4e — Product Strategist Production reliability, latency and payload optimization

Implemented on 2026-08-10. The full server-prepared Product Strategist request remains the redacted, fingerprinted authority for strict preflight and deterministic response validation, but it is no longer serialized wholesale into the provider user message. The focused policy now selects at most 12 genuinely useful Product Strategist files without filling the quota with technical noise, bounds internal context at 24,000 bytes and source excerpts at 3,200 bytes, and keeps the existing 35,000 estimated-token/160,000-byte internal hard ceilings. ## Release gates

Repository Futures ships only when:

- deterministic evidence remains authoritative and provider output remains bounded untrusted enrichment;
- one primary, at most two supports and complete required closure are enforced in domain and UI;
- current Universe truth never becomes a copied Future graph;
- Prepared, Exported, Applied to review branch, PR opened, Pending verification and verification outcomes remain distinct;
- ZIP/manual and GitHub derive from one immutable prepared snapshot;
- GitHub writes stay explicit, branch-only, server-authorized and recoverable;
- verification requires compatible owner/project/repository/branch/scanner/measurement/plan/evidence identity;
- unresolved, incompatible or regressed relationships cannot unlock a Future;
- the complete workflow works without WebGL, hover, motion, color or a mouse;
- gzip, interaction, NodeNext, browser-marker, secret, migration, test, lint, build and human-review gates pass;
- Delivery Pack, Client Handoff, reports, manifests and `score.json` remain truthful compatibility outputs;
- applicable client-facing compliance material retains **This is not legal advice.**
