## Product and Interaction Specification

**Status:** Canonical Ω.18.5a specification — ready for human acceptance  
**Program:** Ω.18.5 — Repository Futures  
**Primary experience:** Future Pathways  
**Primary output:** Executable Future Plan  
**Specification date:** 2026-08-06  
**Implementation status:** Documentation contract only; no Repository Futures implementation is authorized until human acceptance  

> **Turn repository evidence into one coherent, executable future.**

---

## 0. Executive decision

Ω.18.5 extends ShipSeal from understanding, improving and verifying a repository into helping the user choose what the repository should become next.

Repository Futures is not a conventional roadmap builder, backlog generator, static flowchart or decorative 3D concept map. Its signature experience, **Future Pathways**, is a living neural decision field that unfolds from the existing Repository Universe and transforms repository-specific evidence into a constrained, reviewable and executable future plan.

The program is governed by one canonical product rule:

> **One primary path**  
> **+ up to two compatible supporting goals**  
> **+ automatically required dependencies**  
> **= one coherent executable future plan.**

This rule is both a product promise and a validation invariant. ShipSeal may show alternatives, conflicts, dependencies and saved branches, but it must never leave the user with several competing active plans.

### Final naming

| Layer | Canonical name | Meaning |
| --- | --- | --- |
| Program | **Repository Futures** | The Ω.18.5 product capability and domain model. |
| Signature visual surface | **Future Pathways** | The cinematic, neural decision field derived from Repository Universe. |
| Recommended mode | **Quick Path** | A guided, safe, low-complexity path to one recommended plan. |
| Expert mode | **Deep Configuration** | Full inspection and editing of the same underlying plan draft. |
| Active plan output | **Executable Future Plan** | One validated, fingerprinted plan containing goals, dependencies, gates, artifacts, verification expectations and saved alternatives. |
| Deferred alternatives | **Save for later** | Provenance-preserving alternatives that are not active in the current plan. |

### Canonical product flow

```text
scan
→ current Repository Universe
→ Future Pathways
→ one Future draft
→ deterministic synthesis
→ prepared immutable Future Plan
→ export or explicit GitHub apply
→ later compatible rescan
→ authoritative verification
→ evidence-backed future unlock
```

### 1.1 Existing source-aligned requirements

The following are treated as pre-existing constraints rather than new decisions:

- The repository’s current truth comes from one authoritative Repository Universe model.
- Current, proposed, applied, verification and future visuals are overlays or derived views of that one model, not competing graph authorities.
- Repository evidence is deterministic and authoritative; Deep Intelligence may enrich meaning but may not invent current facts, permissions, execution, mutation or verification.
- The truthful lifecycle remains strict: `Proposed != Prepared != Exported != Applied to review branch != PR opened != Verified`.
- ZIP export is non-mutating; a created PR is not a merge; Applied to review branch and PR opened remain pending until compatible rescan evidence exists.
- GitHub mutation requires preflight, bounded preview, explicit confirmation, server-side authorization and provider-confirmed results.
- A later compatible scan, not animation or provider language, determines verified, partially verified, unresolved, regressed or incompatible outcomes.
- The experience must remain usable without WebGL, motion, hover or color.
- Light, Dark and System themes, reduced motion, mobile, keyboard, touch, focus, readable long identifiers and non-color legends remain first-class requirements.
- Heavy graph, prompt, ZIP, PDF and provider work must not be pulled into initial or landing bundles.
- Server-reachable ESM imports must remain NodeNext-safe and the function typecheck remains a release gate.

This document resolves the following areas that were directional but not yet fully specified:

- the canonical visual grammar for current truth versus possible futures;

## 2. Evaluation of the handoff and current product vision

## 2.1 What the handoff gets right

The handoff is a strong, implementation-aware foundation because it protects the most important ShipSeal contracts before introducing the new experience.

### A. It preserves current repository truth

The proposed future field is explicitly an overlay on the authoritative Repository Universe. This prevents the most dangerous conceptual regression: showing desired future capabilities as if they already exist in the repository.

### B. It connects vision to execution

The handoff does not stop at ideation. It joins future selection to existing proposal generation, prepared-plan review, ZIP/PR routes, authoritative rescan verification and evidence-backed future unlocks.

### C. It constrains AI authority correctly

Deep Intelligence may propose future directions and rationale, but deterministic ShipSeal remains responsible for evidence, safety, compatibility, dependency closure, lifecycle, persistence, mutation and verification.

### D. It anticipates accessibility and performance early

The requirement that Future Pathways work without WebGL, motion, hover or color is correctly placed in the initial contract. The existing Universe and application bundle sizes make this essential rather than optional.

### E. It proposes an independently reviewable sprint sequence

The a–g sequence correctly separates specification, deterministic model, guided synthesis, visualization, artifacts, verification and release hardening.

## 2.2 What needed further resolution

The handoff intentionally leaves several product questions open. Without resolving them, an implementation could still become a beautiful but ambiguous concept graph.

### A. The neural field needed a semantic visual grammar

It was not yet precise enough how a user distinguishes:

- current repository truth;
- candidate futures;
- selected goals;
- automatically required dependencies;
- already satisfied dependencies;
- conflicts;
- generated artifacts;
- human-review gates;
- verification gates;
- saved alternatives;
- verified unlocks.

This specification assigns a visual and textual contract to each.

### B. Quick Path needed a firm decision model

The handoff said ShipSeal ranks primary futures and synthesizes dependencies plus supporting goals, but it did not fully specify when supporting goals are suggested, preselected, removable or blocked.

This specification establishes that Quick Path:

1. asks the user to choose or confirm one primary goal;
2. recommends zero to two supporting goals;
3. may show them preselected in the draft, but never prepares or applies the plan without review and confirmation;
4. automatically includes required dependencies visibly;
5. produces exactly one active draft.

### C. Deep Configuration needed guardrails

An expert surface can easily become a second plan engine. This specification requires both modes to edit the same canonical draft, obey the same constraints and converge on the same validated output.

### D. “Save for later” needed lifecycle meaning

Saved branches are not active goals, hidden work or abandoned concepts. They retain their source candidate, evidence, compatibility reason, exclusion reason and lineage to the plan from which they were deferred.

### E. “Future unlocked” needed a strict truth boundary

A future becomes unlocked only from compatible verification evidence or a deterministically satisfied dependency state. It is not unlocked because a prompt was generated, a ZIP was downloaded, a PR was opened or a model predicted success.

## 2.3 Fit with the long-term ShipSeal vision

Repository Futures is a strong extension of the Living Repository vision because it changes the user’s relationship with repository intelligence:

- Repository Universe answers: **What exists and how is it connected?**
- Improve answers: **What should be fixed now?**
- Verify answers: **What changed according to compatible evidence?**
- Repository Futures answers: **What coherent capability should this repository become next?**

It also strengthens ShipSeal’s primary identity as an AI Repository Intelligence Platform rather than reverting to report generation. The signature output is first experienced spatially and causally, then converted into reviewable artifacts and execution routes. Reports remain supporting evidence and delivery material.

## 2.4 Product risk assessment

| Risk | Why it matters | Required response |
| --- | --- | --- |
| Decorative sci-fi spectacle | Could violate “motion explains intelligence” and reduce trust. | Every visual event must map to a model state, evidence relationship or execution consequence. |
| Too many possible futures | Could create decision paralysis and resemble a roadmap tool. | One-primary/two-supporting invariant; alternatives move to Save for later. |
| Future shown as current | Could fabricate repository capabilities. | Currentness is encoded in geometry, material, labels, lifecycle and DOM text. |
| AI recommendation overreach | Could make provider output appear authoritative. | Deterministic eligibility and validation; provider origin disclosed; fallback remains complete. |
| Parallel plan engines | Quick and Deep could drift. | One draft, one synthesis engine, one fingerprint, one validation contract. |
| Heavy 3D regression | Could harm mobile and initial-load performance. | Existing lazy Universe renderer, derived overlay, performance budgets, DOM-first equivalent. |
| Lifecycle inflation | “Prepared” or “PR created” could look complete. | Explicit lifecycle language and gated visual transitions. |
| Verification overclaim | Could imply production correctness or causation. | Repository evidence only; compatible-boundary requirements; limitations remain visible. |

## 3. Product scope

## 3.1 Primary user outcome

After scanning and understanding a repository, a user can choose one evidence-supported future direction and receive one coherent plan that ShipSeal can prepare, review, export or apply through the existing safe workflow, then verify through a later compatible scan.

## 3.2 Core user stories

### Guided builder

> I want ShipSeal to recommend the most valuable safe next direction, explain why it fits my repository and turn it into one reviewable plan without forcing me to understand the entire graph.

### Expert builder

> I want to inspect the evidence, dependencies, conflicts, gates, artifacts and prompt packs, then adjust the plan without losing coherence or creating a competing plan.

### Repository owner

> I want every proposed change and claimed outcome to remain traceable to repository evidence and compatible verification.

### Cost-conscious AI user

> I want the plan and prompt packs to direct coding agents toward the right files, sequence and verification gates without repeatedly loading irrelevant repository context.

### Returning user

> I want a later scan to show which parts of the planned future are verified, unresolved or regressed, and which new futures are now legitimately unlocked.

## 3.3 In scope

- future candidate synthesis from existing deterministic evidence, supported proposals, validated Deep Intelligence candidates and verified opportunity signals;
- candidate ranking and explainability;
- exactly one primary goal;
- zero to two compatible supporting goals;
- automatic, visible transitive dependency closure;
- hard and soft conflict detection;
- Save for later lineage;
- one versioned Executable Future Plan;
- cinematic Future Pathways overlay on the one Repository Universe;
- Quick Path and Deep Configuration;
- plan gates, artifacts, prompt packs, review and apply/export integration;
- later compatible rescan verification and evidence-backed future unlocks;
- DOM/list, reduced-motion, keyboard, touch and mobile equivalents;
- performance and security release gates.

## 3.4 Explicitly out of scope

Unless separately specified, Ω.18.5 does not include:

- autonomous code execution;
- autonomous repository mutation;
- direct pushes to `main`;
- automatic PR merge;
- deployment execution or deployment verification;
- scheduled/background rescans;
- webhook-triggered rescans;
- multiple simultaneous active plans;
- cross-repository Futures;
- a generic project-management roadmap;
- team collaboration, assignments, approvals or organization governance;
- public sharing or badges;
- payment or entitlement logic;
- exact token-cost prediction;
- numeric ROI, effort, time, token-saving or success predictions;
- legal or compliance certification;
- proof of production behavior, causation or business impact;
- provider-generated repository facts without deterministic evidence;
- autonomous model/provider selection;
- automatic cleanup of partial GitHub branches;
- a second Repository Universe model or renderer authority.

## 4. Canonical domain language

| Term | Definition |
| --- | --- |
| Current repository truth | Evidence-backed entities and relationships in the authoritative Repository Universe for the active scan snapshot. |
| Future candidate | An evidence-linked possible goal that has not been selected. |
| Primary goal | The single defining outcome around which the active plan is synthesized. Exactly one is required for a valid plan. |
| Supporting goal | A compatible secondary outcome that strengthens the primary goal without creating a competing plan. Zero to two are allowed. |
| Required dependency | A capability, artifact, prerequisite or gate that must be satisfied for an active goal. It is included automatically and visibly. |
| Optional dependency | A beneficial but non-mandatory prerequisite that may become a supporting goal, artifact or saved alternative. |
| Dependency closure | The complete cycle-safe transitive set of required dependencies for the selected goals. |
| Satisfied dependency | A dependency already supported by current repository evidence. It remains visible but does not generate unnecessary work. |
| Conflict | A detected incompatibility, contradiction, collision, unsupported action, unsafe target, stale identity or insufficient evidence condition. |
| Gate | A required decision or validation boundary before the plan can advance. |
| Artifact | A generated or reviewed repository file, plan document, manifest or prompt-pack output tied to one or more active goals. |
| Outcome | A truthful lifecycle result such as Prepared, Exported, Applied to review branch, PR opened, Pending verification, Verified, Partially verified, Unresolved, Regressed or Incompatible. |
| Saved branch | A future candidate excluded from the active plan but retained with provenance and exclusion rationale. |
| Future unlock | A future candidate newly eligible because compatible evidence shows a prerequisite capability or dependency is satisfied. |
| Executable Future Plan | The single validated and fingerprinted plan containing goals, dependency closure, conflicts, gates, artifacts, verification expectations and saved alternatives. |

### 4.1 Canonical versioned contract names

Ω.18.5b–Ω.18.5f must use these initial contract identities unless a reviewed migration replaces one before implementation:

- `shipseal.repository-future-graph.v1`;
- `shipseal.repository-future-draft.v1`;
- `shipseal.repository-future-synthesis.omega18.5.v1`;
- `shipseal.repository-future-prepared-plan.v1`;
- `shipseal.repository-future-artifacts.v1`;
- `shipseal.repository-future-prompt-pack.v1`;
- `shipseal.repository-future-persistence.v1`;
- `shipseal.repository-future-verification.v1`.

Fingerprints derive only from normalized inputs, stable ordering, explicit schema/policy versions, stable repository/project/scan identity and explicitly identified acknowledgement inputs. Timestamps, animation state, display order, request IDs and other non-deterministic values are excluded from identity.

### 4.2 Conceptual future node contract

Every future-graph node must eventually contain:

- stable ID and schema version;
- node kind and lifecycle;
- currentness;
- title and repository-specific rationale;
- deterministic, provider or verified-signal origin;
- evidence IDs and repository-relative evidence paths;
- confidence tier and human-review state;
- optional stable `universeNodeId` mappings to current truth;
- limitations and explicitly unavailable information;
- deterministic content fingerprint.

Required node kinds are `repository-entity`, `future-goal`, `capability`, `artifact`, `gate` and `outcome`. Primary, supporting, required dependency, optional dependency and Save for later are path roles, not competing node kinds. A future overlay references current Universe identities; it never copies current truth into a second graph authority.

## 5. The canonical plan rule

## 5.1 Invariant

A valid Executable Future Plan contains:

- exactly one primary goal;
- zero, one or two supporting goals;
- all required transitive dependencies;
- no unresolved hard conflicts;
- an ordered set of gates;
- an ordered and bounded artifact set;
- explicit verification expectations;
- a deterministic fingerprint;
- any excluded valuable alternatives in Save for later.

## 5.2 Why only one primary path

The primary path defines the dominant repository transformation and gives the plan a single coherent narrative, execution order and verification target. It prevents the product from producing a bundle of unrelated “good ideas.”

## 5.3 What qualifies as a supporting goal

A supporting goal is valid only when all of the following are true:

1. it is compatible with the primary goal;
2. it is compatible with every other active supporting goal;
3. it shares, strengthens or efficiently extends the primary dependency closure;
4. it does not introduce a second dominant outcome;
5. its artifact targets do not create unresolved collisions;
6. its verification expectations can coexist with the primary plan;
7. it remains bounded enough that the plan still has one understandable execution narrative.

A goal that fails these rules must be excluded, replaced or saved for later.

## 5.4 Required dependencies are automatic but never hidden

When a goal requires a dependency, ShipSeal adds it automatically to the draft. The user must see:

- what was added;
- why it is mandatory;
- which active goal requires it;
- the evidence supporting the requirement;
- whether it is already satisfied, partially satisfied, missing or unavailable;
- what artifact or human action can satisfy it;
- what happens if the primary or supporting goal is removed.

A required dependency cannot be manually removed while the requiring goal remains active. The user may instead:

- remove or replace the requiring goal;
- resolve an incorrect relationship through a human-review path;
- mark an external/manual prerequisite with evidence and review status;
- save the affected goal for later.

## 5.5 One plan, not several plan variants

ShipSeal may show alternate primary candidates and saved branches, but only one active draft exists at a time. Changing the primary goal transforms the same draft and recomputes supporting goals, dependencies, conflicts, artifacts and fingerprint.

The UI must not present “Plan A / Plan B / Plan C” as simultaneously active deliverables.

## 6. Candidate eligibility, ranking and synthesis

## 6.1 Candidate inputs

Future candidates may be derived from:

- Repository Health frictions;
- Workspace Story evidence;
- authoritative Repository Universe entities and relationships;
- current transformation domains;
- supported generator-backed proposal families;
- actionable improvement lifecycle and artifact contracts;
- validated Deep Intelligence `future-direction` findings;
- compatible Ω.18.4 opportunity signals;
- satisfied or unresolved dependency states;
- current prepared, applied and verification history where owner/project/repository identity is compatible.

## 6.2 Eligibility gates

A candidate may enter the selectable future field only if:

- it has a stable identity;
- it has repository-specific rationale;
- it references valid evidence IDs, paths or compatible opportunity signals;
- its currentness is explicitly non-current unless already satisfied;
- its confidence and origin are known;
- its intended artifact family or human action is supported or explicitly marked unavailable;
- it has no unresolved security rejection or sensitive-output violation;
- it does not claim successful commands, permissions, mutation, merge, deployment or verification without evidence.

Candidates that fail eligibility do not silently disappear. They appear, where useful, as unavailable or limited findings with the reason disclosed outside the active selection field.

## 6.3 Deterministic ranking order

Ranking must be deterministic, explainable and stable for identical bounded inputs. It uses an ordered comparison rather than an opaque single “AI score.”

Canonical comparison order:

1. **Eligibility and absence of blockers** — blocked or ineligible candidates never outrank executable candidates.
2. **Alignment with repository friction** — direct response to material current evidence before generic benefit.
3. **Evidence quality and coverage** — deterministic, repository-specific support before bounded inference.
4. **Satisfiable dependency closure** — complete and achievable prerequisites before unresolved burden.
5. **Supported artifact generation** — validated generators, destinations and review paths before unsupported output.
6. **Verification feasibility** — ability to define compatible later-scan evidence.
7. **Sensitive-review burden** — lower burden only after safety, relevance and evidence criteria.
8. **Stable ID** — deterministic final tie-breaker.

The UI must explain the leading reasons in plain language, not expose a meaningless composite score as the primary rationale.

Approved user-facing fit tiers are `Strong evidence fit`, `Supported with review`, `Exploratory` and `Blocked`. Qualitative trade-offs may describe focused versus cross-cutting impact; small, moderate or broad change weight; low, moderate or high verification burden; direct, review-dependent or uncertain reversibility; sensitive review; known conflicts; and unavailable information. Every trade-off cites its evidence basis. Numerical success probability, ROI, implementation hours, token savings, time savings and projected score improvement are prohibited.

## 6.4 Primary selection

- Quick Path recommends a short ranked set, normally three candidates and never more than five in the first view.
- The user explicitly selects or confirms one primary goal.
- ShipSeal may mark one candidate as **Recommended**, but recommendation is not selection or confirmation.
- If only one candidate is eligible, the UI still asks the user to confirm it.
- If no candidate is safely eligible, Future Pathways enters an honest **No executable future yet** state with the evidence or dependency needed next.

## 6.5 Supporting-goal synthesis

After primary selection, ShipSeal evaluates compatible supporting goals.

- Quick Path recommends zero to two.
- They may appear preselected in the draft when compatibility is strong and the additional burden is bounded.
- Each preselection clearly states that it is recommended and removable before plan confirmation.
- A supporting goal is never added after the plan is prepared without producing a new draft fingerprint.
- When no supporting goal improves coherence, the plan remains primary-only.
- Deep Configuration may replace, add or remove supporting goals but cannot exceed two or bypass compatibility rules.

## 6.6 Dependency closure

For the active goal set, ShipSeal computes cycle-safe transitive dependency closure.

Each dependency has:

- required or optional status;
- requiring goal IDs;
- evidence and rationale;
- satisfaction state;
- origin;
- available artifact/action;
- conflict state;
- verification expectation;
- human-review requirement.

Cycles are not rendered as endless loops. A required-dependency cycle is a blocking hard conflict: preparation is prohibited and the complete ordered cycle is identified. Optional cycles may be collapsed for inspection only when they do not enter required closure.

## 6.7 Conflict classes

| Class | Meaning | Plan effect |
| --- | --- | --- |
| Hard | Unsafe target, contradictory dependency, unsupported mutation, stale identity, unresolved path collision, incompatible verification boundary or impossible action. | Blocks preparation until resolved, goal replaced or branch saved for later. |
| Soft | Competing sequencing, high review burden, optional target overlap, weak compatibility or excessive scope. | Plan may continue only after an explicit resolution choice. |
| Informational | Limitation, uncertainty, provider hint or non-blocking tradeoff. | Does not block, but remains visible in rationale and review. |

Required conflict families are incompatible goals, dependency contradiction, dependency cycle, unsafe or sensitive target, artifact-path collision, contradictory create/update/strengthen action, insufficient evidence, stale repository identity, foreign scan or project identity, incompatible verification boundary, unsupported generator and unresolved human-review requirement. Every blocking conflict records severity, evidence, affected nodes and at least one truthful recovery action.

## 6.8 Save for later

When a candidate is not active but remains valuable, ShipSeal stores it as a saved branch with:

- candidate ID and origin;
- evidence lineage;
- the active plan fingerprint from which it was deferred;
- exclusion reason;
- conflicts or unmet dependencies;
- compatibility notes;
- the condition under which it may become eligible or recommended;
- timestamp/snapshot identity when persisted.

Saving is non-mutating and does not imply future execution.

## 6.9 Deterministic synthesis order

The synthesis engine must execute this stable sequence:

1. normalize candidates from repository frictions, transformation proposals, Repository Intelligence, supported generator capabilities, validated Deep Intelligence future directions and eligible verified opportunity signals;
2. reject stale, foreign-project/repository, unsafe, evidence-free, unsupported and invalid provider-only candidates;
3. require exactly one primary goal;
4. validate zero to two supporting goals;
5. compute transitive required-dependency closure;
6. detect required-dependency cycles;
7. detect compatibility conflicts;
8. detect artifact collisions;
9. merge duplicate capabilities and compatible artifact targets;
10. resolve create/update/strengthen operations against current evidence;
11. topologically order dependencies, gates, artifacts and outcomes;
12. move viable unselected candidates to Save for later;
13. emit one normalized draft and fingerprint;
14. during preparation, revalidate every identity, path, content fingerprint, limitation and acknowledgement.

Provider text alone can suggest a dependency but cannot make it executable, satisfied or required without deterministic validation.

## 7. Executable Future Plan contract

## 7.1 Required plan contents

A plan must contain the following conceptual sections:

1. **Identity** — schema version, plan ID, source scan identity, owner/project/repository/branch scope and deterministic fingerprint.
2. **Primary goal** — title, repository-specific rationale, evidence, confidence and expected outcome.
3. **Supporting goals** — zero to two, each with compatibility explanation.
4. **Dependency closure** — required dependencies and their satisfaction states.
5. **Conflicts and resolutions** — detected conflicts, severity, chosen resolution and human-review state.
6. **Execution sequence** — ordered stages that respect dependencies and gates.
7. **Artifacts** — generated/reviewed files, actions, destinations, sources and fingerprints.
8. **Prompt packs** — explicitly chosen supported model adapters generated from the same canonical plan.
9. **Gates** — specification, evidence, conflict, review, snapshot, mutation and verification gates.
10. **Verification contract** — expected artifact, statement and graph evidence for a later compatible scan.
11. **Saved alternatives** — deferred branches with provenance.
12. **Limitations** — evidence gaps, unsupported actions, provider limitations and non-claims.

## 7.2 Plan coherence test

A plan is coherent only if:

- the user can state its primary outcome in one sentence;
- every active goal contributes to that outcome;
- every required dependency has a reason and a resolution path;
- every artifact traces to an active goal or required dependency;
- every execution stage has an entry gate and expected evidence;
- no hard conflict remains unresolved;
- all selected artifacts can share one prepared snapshot;
- ZIP and PR routes would use the same artifact identities and content fingerprints;
- later verification expectations are defined before apply/export.

## 7.3 Plan lifecycle

The future-plan lifecycle is additive to, not a replacement for, existing truth states.

1. **Candidate** — eligible future direction, not selected.
2. **Selected** — chosen as primary or supporting, draft not yet coherent.
3. **Synthesizing** — dependency closure and conflicts being computed.
4. **Draft** — one active plan exists but gates may remain unresolved.
5. **Coherent draft** — goal and dependency rules pass; user can review artifacts and gates.
6. **Prepared** — artifact set and prepared snapshot are validated.
7. **Exported** — non-mutating package downloaded; not Applied to review branch.
8. **Applied to review branch** — provider-confirmed branch mutation according to the apply contract; not merged and not Verified.
9. **PR opened** — GitHub confirms the review PR exists; distinct from branch application, merge and verification.
10. **Pending verification** — later compatible scan has not yet supplied sufficient evidence.
11. **Verified / Partially verified / Unresolved / Regressed / Incompatible** — synthesized from the authoritative verification relationship.
12. **Future unlocked** — a new candidate becomes eligible from compatible verified evidence; this state belongs to the new candidate, not as proof that all previous outcomes succeeded.

## 8. Information architecture and workspace placement

## 8.1 Relationship to the four chapters

Repository Futures is introduced from **Improve** after the repository has been understood, while its visual field uses the existing Repository Universe stage.

Recommended product placement:

- **Understand:** current repository truth and Universe.
- **Improve:** current frictions, immediate proposals and entry to Repository Futures.
- **Future Pathways mode:** a focused transformation of the Universe stage that spans Improve while retaining access to evidence inspection.
- **Verify:** later-scan outcomes for applied or exported plans.
- **Deliver:** final packages, reports and exports.

Future Pathways must not become a fifth competing top-level chapter in Ω.18.5. It is an advanced Improve experience that reuses the Universe rather than duplicating navigation.

## 8.2 Entry points

Primary entry:

- **Plan the repository’s next future** from Improve.

Contextual entry:

- a verified opportunity signal can offer **Explore newly unlocked future**;
- a current friction or Universe selection can offer **See futures this affects**;
- a saved project can reopen its last future draft or verified outcome when persistence exists.

## 8.3 Exit points

The user may exit Future Pathways to:

- return to current Universe truth;
- review the coherent plan;
- prepare artifacts;
- export a non-mutating package;
- preview/confirm GitHub application;
- open Verify after a later scan;
- save alternatives for later.

Leaving the field must not silently discard a confirmed draft. Anonymous unsaved state requires an explicit warning if meaningful edits would be lost.

## 9. Future Pathways — signature experience specification

## 9.1 Experience statement

Future Pathways should feel as though the repository’s current knowledge begins generating plausible future trajectories around itself. The user does not open a roadmap. The current Repository Universe remains spatially grounded, then evidence-linked possibilities emerge as a luminous but clearly non-current neural field.

The experience is cinematic, but every visible event has semantic meaning.

## 9.2 Spatial model

### Current core

- The existing Repository Universe occupies the grounded inner space.
- Current repository nodes retain their established positions, identity and evidence semantics.
- The central repository node remains the orientation anchor.
- Current nodes use solid, stable geometry and restrained motion.

### Future horizon

- Future candidates emerge outside or beyond the current core, never inside it as if they already existed.
- Candidate goals occupy a future horizon shell whose distance reflects current execution readiness and dependency burden, not chronology.
- A candidate closer to the core is more immediately reachable; distance is always explained textually.
- Supporting goals appear in neighboring compatible sectors, not as equal competing centers.
- Required dependencies form visible bridges between current evidence and future goals.

### Selected pathway corridor

Once a primary goal is selected:

- the field reorients around one dominant corridor from current truth to the primary goal;
- compatible supporting goals align as side branches that rejoin the same corridor;
- required dependencies settle into ordered stepping nodes along the route;
- artifacts and gates appear nearer to the execution corridor;
- unrelated candidates recede but remain accessible as saved or alternative futures.

The field must visually converge, not expand indefinitely.

## 9.3 Node taxonomy and visual contract

Visual details must be encoded by more than color. Shape, material, border, label, iconography, position and DOM text work together.

| Node kind | Meaning | Visual behavior |
| --- | --- | --- |
| Current repository entity | Existing file, folder, concept, workflow or evidence-backed entity. | Solid geometry, stable position, established Universe material, current/evidence label. |
| Future candidate goal | Possible non-current outcome. | Translucent or refractive outer form, hollow core, future label, subtle incoming evidence filaments. |
| Selected primary goal | Dominant active future. | Largest future node, persistent halo/ring, primary badge, central pathway alignment. |
| Supporting goal | Compatible secondary outcome. | Smaller companion form, linked to primary corridor, numbered support badge. |
| Capability in required-dependency role | Mandatory prerequisite. | Bridge/junction geometry placed on route; lock/requirement symbol and reason. |
| Capability in satisfied-dependency role | Current capability already evidenced. | Grounded bridge anchored to current node, completion mark and evidence link; no artificial work pulse. |
| Capability in optional-dependency role | Beneficial but non-mandatory. | Dashed outline or side orbit; never mistaken for required. |
| Artifact | Generated or reviewed repository output. | Document-like shard/plate attached to the stage that produces it; action and destination shown in inspector. |
| Gate | Human or system boundary. | Threshold plane, ring or checkpoint across the corridor; progression pauses until resolved. |
| Conflict | Incompatibility or blocked state. | Visible fracture/crossing interruption, non-color icon, severity label; never just red glow. |
| Outcome | Prepared, exported, applied or verified result. | State seal attached only after corresponding lifecycle evidence. |
| Saved branch | Deferred alternative. | Dimmed but retained branch outside active corridor with bookmark/lineage badge. |
| Future unlock | Newly eligible candidate from verification. | Emerges from verified evidence with a distinct unlock event and provenance link. |

## 9.4 Edge taxonomy

| Edge | Direction and meaning | Visual behavior |
| --- | --- | --- |
| supports | Supporting evidence/capability → supported goal or capability. | Stable thin filament; impulse flows toward supported node when inspected. |
| requires | Dependent goal/capability → required capability. | Strong directed bridge; repeated but calm directional marker. |
| conflicts-with | Symmetric incompatibility, serialized once by stable endpoint order. | Interrupted crossing, warning glyph and explicit conflict inspector. No continuous distracting pulse. |
| produces | Goal/capability/stage → artifact. | Directed formation line ending at artifact shard. |
| gates | Gate → lifecycle transition or gated stage. | Corridor narrows or pauses at the gate plane. |
| verifies | Later evidence/outcome → artifact, statement or capability verified. | Dotted future-facing line until verification; solid only after compatible evidence. |
| unlocks | Verified evidence/capability → newly eligible future candidate. | One-time reveal impulse from evidence/outcome to unlocked candidate. |
| save-for-later-lineage | Active draft/prepared plan → deferred candidate. | Fine bookmark filament shown on request, not part of active energy flow. |

Edge animation is event-driven. There is no ambient traffic on every edge.

## 9.5 Energy impulse semantics

Energy impulses are the primary “neural” motion language. They must communicate a real transition.

Allowed impulses:

- evidence flowing from current nodes into a candidate rationale;
- compatibility evaluation between primary and supporting goals;
- dependency closure propagating from selected goals;
- artifact production from an execution stage;
- a gate accepting or blocking progression;
- verified evidence unlocking a future candidate;
- selection focus travelling along the active path.

Disallowed impulses:

- random perpetual particles;
- pulses implying execution while the plan is only selected or prepared;
- success bursts before provider confirmation or compatible verification;
- activity on unrelated background nodes solely for visual richness.

## 9.6 Current-versus-future visual grammar

The distinction must survive grayscale, reduced motion and screenshots.

### Current truth

- solid forms;
- stable positions;
- existing evidence badges;
- normal labels;
- no “possible” wording.

### Candidate future

- hollow/translucent forms;
- outer horizon placement;
- explicit **Candidate future** label;
- evidence-linked rationale;
- no completion seal.

### Selected future

- persistent selection ring;
- role label: Primary or Supporting;
- active corridor connection;
- draft state visible.

### Prepared future

- plan fingerprint and prepared seal attached to plan summary, not to repository nodes as if current.

### Applied-to-review-branch future

- applied-operation/PR evidence appears in the plan timeline;
- future nodes remain non-current until later scan evidence supports current capability.

### Verified future

- only compatible later-scan evidence may ground a previously future capability into the current Universe overlay;
- the visual transition must say **Observed after compatible rescan**, not “ShipSeal caused this.”

## 9.7 Canonical cinematic choreography

The full-motion sequence is concise, interruptible and state-driven:

1. **Settle** — current Universe motion settles and current truth becomes stable.
2. **Open horizon** — the future plane appears while the current repository remains grounded.
3. **Evidence transmission** — one impulse per evidence group travels toward eligible candidates.
4. **Candidate emergence** — candidates appear only after their evidence relationship is visible or textually announced.
5. **Primary selection** — one chosen future receives persistent emphasis; incompatible paths recede with explicit textual state.
6. **Dependency closure** — required capabilities appear in topological order with reasons and dependent goals.
7. **Supporting convergence** — zero to two compatible supporting goals join the one primary corridor.
8. **Synthesis** — flow follows dependency → goal → artifact → gate order.
9. **Crystallization** — successful preparation produces one stable plan object with fingerprint, artifact count, gates and Prepared state.
10. **Apply or export** — visual progress advances only when the corresponding operation stage actually completes.
11. **Rescan** — compatible later-scan evidence traverses mapped current entities.
12. **Verification and unlock** — verified nodes stabilize and only valid persisted evidence-backed unlock edges reveal new futures.

The field becomes calmer after crystallization. Solid pathways mean deterministic support; dashed pathways mean bounded inference. Required dependency paths remain visually distinct from optional support. Conflict paths appear on inspection or invalid selection rather than pulsing continuously. An evidence impulse represents one evidence group, an apply impulse one completed provider operation stage, a verification impulse one artifact/statement result and an unlock impulse one verified unlock event.

Suggested overall cinematic duration: approximately 1.5–2.5 seconds for the initial reveal, with interaction available as early as practical. The sequence must not introduce an artificial loading delay.

## 9.8 Selection choreography

When a primary goal is selected:

- an evidence impulse traces from current supporting nodes to the goal;
- the selected node moves or visually aligns to the dominant route position;
- compatibility evaluation briefly traces to eligible supporting goals;
- zero to two recommendations settle beside the corridor;
- dependency closure propagates backward from goals toward current truth;
- satisfied dependencies anchor immediately;
- missing dependencies form ordered bridge nodes;
- hard conflicts interrupt the corridor and prevent the prepared-state seal;
- the plan summary appears only after synthesis completes.

The user may skip animation and receive the final spatial state immediately.

## 9.9 Conflict choreography

A conflict must feel like a meaningful structural interruption rather than an alarm effect.

- The affected route segment stops before the conflict.
- The conflicting node/edge pair remains visible.
- The inspector explains severity, evidence, consequence and available resolution.
- Quick Path offers one primary resolution action.
- Deep Configuration offers all supported resolution choices.
- No flashing or repeated red pulsing is used.

## 9.10 Gate choreography

Gates are crossed only when the underlying state changes.

Examples:

- evidence sufficiency gate opens when required evidence exists;
- conflict gate opens after a valid resolution;
- human-review gate opens after acknowledgement/approval;
- prepared-snapshot gate opens after validation;
- mutation gate opens only after explicit confirmation and provider success;
- verification gate opens only after compatible later-scan synthesis.

An opening gate is not equivalent to a completed future. It allows progression to the next lifecycle stage.

## 9.11 Verification and unlock choreography

After a compatible later scan:

1. the current Universe loads from the later validated snapshot;
2. the verification overlay marks artifact, statement and graph outcomes;
3. the previous path appears as historical lineage, not an active future draft;
4. verified capabilities become grounded current evidence where supported;
5. partially verified or unresolved segments remain incomplete;
6. regressions create explicit warning branches;
7. only validated opportunity signals may emit an unlock impulse;
8. newly eligible future candidates appear with **Unlocked by verified evidence** and source relationship identity.

## 9.12 Camera and framing

- The camera never auto-flies for long distances without user control.
- Primary selection may reframe the active corridor, but preserves orientation anchors.
- Current repository core remains visible or recoverable with one action.
- “Reset view” returns to the current report-derived frame.
- “Focus path” frames the active corridor.
- “Focus evidence” frames the current nodes supporting the selected goal.
- Fullscreen is optional, not required for completion.
- Mobile uses guided framing rather than free complex 3D navigation as the default.

## 9.13 Labels and copy density

Default field copy:

- one headline;
- one sentence explaining the current decision;
- no more than three candidate cards/labels in the initial Quick Path view;
- no long technical paragraphs on the canvas;
- evidence, confidence, dependencies and limitations live in contextual inspection;
- lifecycle terms remain explicit and consistent.

Recommended primary headline patterns:

- **Choose the repository’s next future.**
- **One path. One executable plan.**
- **This future is supported by your repository evidence.**

Avoid:

- “AI predicts your future”;
- “Guaranteed outcome”;
- “Autonomous transformation”;
- “Completed” before compatible verification;
- “Best” without an explainable comparison boundary.

## 10. Quick Path specification

## 10.1 Purpose

Quick Path is the default mode for users who want ShipSeal to reduce complexity while preserving evidence, control and review.

## 10.2 Entry state

The user sees:

- a recommended primary candidate;
- up to two meaningful alternatives;
- one-sentence repository-specific rationale for each;
- evidence strength and limitation state;
- a clear action to choose or confirm the primary future;
- a secondary action to open Deep Configuration.

## 10.3 Guided flow

### Step 1 — Choose one future

The user selects one primary goal. Recommendation is visible but not auto-confirmed.

### Step 2 — See the coherent bundle

ShipSeal synthesizes:

- zero to two recommended supporting goals;
- all required dependencies;
- satisfaction states;
- detected conflicts;
- expected artifacts;
- verification method.

### Step 3 — Resolve the one blocking issue

If a hard conflict exists, Quick Path shows the highest-priority blocker and one recommended resolution. Additional detail is disclosed on request.

### Step 4 — Review the plan story

The user sees a concise sequence:

1. what changes first;
2. what capability that enables;
3. what files/artifacts are prepared;
4. where human review is required;
5. how later verification will work.

### Step 5 — Prepare one plan

The user explicitly selects **Prepare plan**. Preparation revalidates the coherent draft, records the selected goal set and creates one immutable, fingerprinted prepared snapshot. Draft edits after this point create a new draft revision; they never mutate the prepared snapshot.

### Step 6 — Review artifacts and route

The user reviews generated files and chooses:

- export/non-mutating package; or
- GitHub preview and explicit apply confirmation.

## 10.4 Quick Path supporting-goal behavior

- Supporting recommendations may be preselected only after primary selection.
- Preselected support is visibly labeled **Recommended support**.
- The user can remove it before confirmation.
- Removing support recomputes dependencies and artifacts immediately.
- Quick Path does not allow more than two.
- Adding a non-recommended goal requires Deep Configuration.

## 10.5 Quick Path conflict behavior

- One blocker at a time is foregrounded.
- The default action favors safety and coherence.
- Hard conflicts cannot be bypassed with a generic “continue anyway.”
- A conflicting future can be saved for later.
- Unsupported or sensitive actions remain unavailable.

## 10.6 Quick Path completion screen

The completion state shows:

- primary goal;
- supporting goals;
- automatically included dependencies;
- number and classes of artifacts;
- required human-review gates;
- chosen prompt-pack targets;
- verification expectations;
- plan fingerprint/identity in disclosure;
- primary action: **Review executable plan**.

It does not show a generic dashboard of scores.

## 11. Deep Configuration specification

## 11.1 Purpose

Deep Configuration gives expert users full visibility into the same future graph and active draft without weakening ShipSeal’s truth, safety or coherence rules.

## 11.2 Same-draft invariant

Quick Path and Deep Configuration share:

- the same candidate graph;
- the same active primary goal;
- the same supporting-goal limit;
- the same dependency closure;
- the same conflicts;
- the same artifact identities;
- the same verification expectations;
- the same plan fingerprint rules;
- the same prepared snapshot.
- the same draft revision and acknowledgements.

Switching modes changes disclosure and editing controls, not underlying truth.

## 11.3 Expert controls

Deep Configuration may expose:

- candidate filters by domain, origin, confidence and readiness;
- current/future/saved/verified layers;
- evidence and provenance inspector;
- compatibility matrix for the active goal set;
- dependency graph and satisfaction states;
- conflict list and resolution choices;
- artifact families, destinations and actions;
- gate sequence;
- verification expectations;
- prompt-pack target selection;
- Save for later collection;
- plan diff from the last confirmed draft.

## 11.4 Allowed edits

The user may:

- replace the primary goal;
- add/remove up to two compatible supporting goals;
- inspect and choose among valid conflict resolutions;
- include supported optional artifacts;
- exclude optional artifacts when plan coherence remains valid;
- select explicitly supported model-specific prompt packs;
- acknowledge human-review gates;
- save alternatives for later;
- revert to ShipSeal’s recommended configuration.

## 11.5 Disallowed edits

The user may not:

- remove a required dependency while its requiring goal remains active;
- exceed two supporting goals;
- keep unresolved hard conflicts and prepare the plan;
- fabricate evidence or mark a dependency satisfied without a supported review/evidence path;
- bypass explicit GitHub confirmation;
- mark Applied to review branch, PR opened or Verified manually;
- create divergent ZIP and PR artifact sets under the same plan fingerprint;
- choose an unsupported prompt target and label it as validated.

## 11.6 Mode switching

- Quick → Deep preserves the active draft and opens the selected entity in context.
- Deep → Quick returns to a concise plan summary if the draft remains valid.
- If Deep changes make the draft invalid, Quick returns to the highest-priority blocker rather than silently repairing the plan.
- “Restore recommended configuration” is explicit and produces a new draft state/fingerprint after confirmation.

## 11.7 Deep Configuration layout

Desktop:

- full-bleed Future Pathways stage;
- compact top toolbar for mode, layers, search and view;
- contextual right inspector;
- collapsible bottom plan sequence or artifact rail;
- conflicts/gates surfaced contextually, not as permanent dashboard cards.

Mobile:

- guided current focus with simplified field;
- bottom sheet for candidate, evidence and configuration detail;
- step-based plan rail;
- free 3D orbit is secondary;
- all functions available through DOM controls.

The deterministic Future experience remains complete when enhancement is disabled, cancelled, unavailable, rejected, invalid or over budget.

## 13. Artifacts and model-specific prompt packs

## 13.1 Canonical artifact principle

All generated artifacts derive from the same confirmed Executable Future Plan. No prompt pack or export route may reinterpret the selected goals into a materially different plan.

## 13.2 Minimum future package

A prepared Future package contains, where supported:

- `SHIPSEAL_FUTURE_PLAN.json` — canonical machine-readable prepared plan;
- `IMPLEMENTATION_PLAN.md` — human implementation sequence and review narrative;
- `ARTIFACT_MANIFEST.json` — destinations, operations, fingerprints, readiness and collisions;
- `EVIDENCE_MANIFEST.json` — goal, statement and artifact provenance without source bodies;
- `VERIFICATION_PLAN.md` — compatible later-scan expectations and non-claims;
- reviewed repository artifacts from existing validated generators;
- selected model/tool-specific prompt packs;
- manual apply, recovery and rollback instructions.

`IMPLEMENTATION_PLAN.md` includes repository/baseline identity, the primary and supporting goals, dependency ordering, qualitative trade-offs, artifact destinations and operations, verified commands only, human-review checkpoints, implementation slices, verification expectations, recovery/rollback notes, provenance, limitations and fingerprints. Repository Futures orchestrates existing Repository Intelligence generators; it does not create a parallel generic artifact generator for families those generators already own.

## 13.3 Prompt-pack contract

- The user explicitly chooses supported target models/tools.
- No silent model choice occurs.
- Every pack references the same plan ID and fingerprint.
- Each pack preserves the same goal, dependencies, artifact targets, gates and verification expectations.
- Model adaptation may change formatting, command style or context packaging, not the underlying plan.
- Packs disclose what they do not know and must not claim hidden model reasoning.
- Token Saver, Balanced Productivity and Maximum Reliability operating guidance may shape execution style without changing plan truth.
- Unsupported targets may receive a clearly generic portable prompt only if labeled unvalidated; otherwise they remain unavailable.

Canonical pack paths are:

- `prompts/codex/IMPLEMENT.md`;
- `prompts/claude-code/IMPLEMENT.md`;
- `prompts/cursor/IMPLEMENT.md`;
- `prompts/windsurf/IMPLEMENT.md`;
- `prompts/human/IMPLEMENT.md`.

Every pack includes repository and plan identity, permitted scope, dependency-ordered tasks, exact artifact targets, evidence references, known verified commands, forbidden/sensitive targets, acceptance criteria, stop/escalation conditions, completion-report requirements and the rescan handoff. Tool-specific differences are limited to interaction format, task chunking and supported workflow conventions. Packs are export artifacts by default; repository writes require explicit per-pack selection and normal prepared-plan review.

## 13.4 Artifact collision rules

- create/update/strengthen actions remain explicit;
- handwritten content remains protected;
- duplicate destinations cannot silently overwrite;
- conflicting active goals must resolve destination collisions before preparation;
- ZIP and PR routes share selected artifact IDs and content fingerprints;
- blocked artifacts remain in manifest/review notes but are not written as normal ready files.

## 14. Apply, rescan and future-unlock loop

## 14.1 Preparation and export

- Preparing validates the coherent draft and artifact set.
- Preparation creates the one immutable `PreparedFuturePlanSnapshot`; ZIP/manual and GitHub routes derive from its exact artifact and plan fingerprints.
- Exporting a package is non-mutating.
- Exported does not mean Applied to review branch and never proves manual application.
- Anonymous export remains available where current product contracts allow it.

## 14.2 GitHub application

- The existing connected GitHub App boundary is reused.
- Repository, branch, path, file and precondition checks occur before mutation.
- Bounded diffs are shown before confirmation.
- Explicit confirmation is required.
- The preview is bound to the exact prepared-plan fingerprint, exact preview fingerprint and expected base commit; any relevant repository change after preview invalidates confirmation.
- Provider-confirmed writes determine **Applied to review branch** and provider-confirmed pull-request creation determines **PR opened**.
- No direct-main push and no automatic merge.
- Partial failure retains truthful stage-aware recovery and ZIP/manual fallback.
- Repository Futures must not introduce a third GitHub write protocol. Ω.18.5f must converge Repository Intelligence provenance/handwritten-preservation strengths with Optimization apply’s stricter preview fingerprint, base-commit binding and stage-aware recovery behavior.

## 14.3 Rescan

- Verification starts from the authoritative saved baseline relationship.
- The user initiates the later scan.
- Owner, project, repository, branch, time, scanner, measurement, plan identity and evidence sufficiency compatibility are enforced.
- Incompatible comparisons suppress direct score deltas and future unlocks.

## 14.4 Verification outcomes

The future plan may become:

- Verified;
- Partially verified;
- Unresolved;
- Regressed;
- Incompatible.

Each outcome contains evidence and one honest next action.

## 14.5 Future unlock rule

A new future candidate may be labeled unlocked only when:

- a compatible verification relationship exists;
- a validated opportunity signal or satisfied dependency state exists;
- the signal traces to evidence and source verification identity;
- deterministic eligibility checks pass;
- no hard conflict or stale identity blocks eligibility.
- the overall authoritative relationship is not Unresolved, Incompatible or Regressed.

A generated artifact, exported ZIP, created PR or model claim alone never unlocks a future.

Signal rules for the MVP are strict:

- `risk-detected` may be emitted from compatible regressed evidence;
- `friction-resolved` and `capability-added` require verified contracts;
- `dependency-satisfied` requires every blocking dependency expectation to verify;
- `future-unlocked` requires verified capability/dependency evidence and no relevant regression.

## 14.6 Required Ω.18.5f verification prerequisites

Repository inspection found three gaps that are not shipped Future capabilities:

1. **Measurement eligibility:** `measurementCompatible` contributes an incompatibility reason today but is omitted from the final `compatibility.eligible` expression. Ω.18.5f must make measurement compatibility a mandatory eligibility condition.
2. **Authoritative relationship wiring:** the comprehensive relationship builder is exercised by tests, but production currently persists an adapter around the older Repository Intelligence verification result. Ω.18.5f must wire authoritative baseline identity → compatible later scan → comprehensive relationship builder → lossless persisted relationship → opportunity-signal derivation → Future candidate adapter.
3. **Regressed unlocks:** current pure signal derivation can emit `future-unlocked` for a regressed overall relationship. Ω.18.5f must enforce the MVP signal rules above before any opportunity is shown as an unlocked Future.

Until that production path exists, opportunity signals are implementation inputs under test, not a user-visible claim that futures are already unlocked.

## 16. Performance and bundle budgets

## 16.1 Loading boundaries

- Future engine and field code load only after explicit Future Pathways intent or a closely bounded prefetch condition.
- No Future Pathways code is added eagerly to landing/scan initial routes.
- Prompt-pack generation, ZIP/PDF and Deep Intelligence remain action-loaded.
- The existing Universe renderer is reused; no second Three.js renderer or model authority.
- Candidate model and dependency closure are derived once per relevant input/fingerprint and indexed for interaction.
- Selection, filtering and inspector changes must not rebuild the full current Universe model.

Current implementation note: once a report exists, `ResultWorkspace` can immediately prefetch the existing Universe chunk. This is looser than older viewport-proximity wording. Ω.18.5 must not describe that prefetch as viewport-only, and new Future feature code must remain independently lazy despite the existing Universe behavior.

## 16.2 Interaction budgets

Target product budgets for normal supported repositories:

- Quick Path exposes at most 24 visible validated goal candidates;
- Deep Configuration exposes at most 80 validated candidates;
- primary selection feedback begins within 100 ms;
- normal bounded synthesis completes within 200 ms or exposes visible progress by that point;
- common filter/selection interactions remain responsive within one animation frame where practical and should not block input beyond 50 ms tasks;
- initial main-chunk growth attributable to Repository Futures is at most 10 KiB gzip;
- unopened Result Workspace growth attributable to Repository Futures is at most 15 KiB gzip;
- mobile does not default to expensive ambient effects;
- field density adapts before frame rate becomes unusable;
- DOM mode remains available immediately when the 3D renderer is delayed or unavailable.

Ω.18.5g must measure these thresholds with bounded repository-size fixtures and may tighten them. It must not loosen them or raise existing warning thresholds merely to hide regressions.

## 16.3 Degradation hierarchy

When performance pressure is detected:

1. reduce ambient motion;
2. reduce labels and non-active edge density;
3. simplify materials and impulse effects;
4. constrain camera effects;
5. switch to simplified 3D pathway;
6. offer/use DOM pathway mode.

The model and plan truth do not change with visual degradation.

## 17. Security, privacy and persistence

## 17.1 Security boundaries

- No repository code is executed.
- No secret or raw provider body enters browser assets, saved snapshots, diagnostics or exports.
- Deep Intelligence receives only bounded, redacted, repository-relative context.
- Provider output remains untrusted and strictly validated.
- GitHub credentials and mutation remain server-only.
- NodeNext function compilation and browser server-marker audits remain release gates.

## 17.2 Persistence behavior

Product requirement:

- authenticated saved projects may eventually persist an owner-scoped mutable Future draft/revision, primary and supporting selections, dependency closure, saved lineage, source scan/evidence fingerprints, origins/limitations, chosen prompt targets, immutable prepared plans, applied-operation binding, verification relationship and unlock ledger;
- anonymous drafts remain session-local unless explicitly exported;
- opening a saved future does not rescan, call a provider or mutate GitHub;
- plan persistence stores derived identities, evidence references, states and fingerprints, not raw archives or source contents;
- prepared plans are immutable; editing after preparation creates a new draft revision;
- saved Futures do not silently regenerate or recalculate under a newer algorithm;
- any new migration is forward-only, reviewed, idempotent and included in migration tests;
- if cross-session future-draft persistence is deferred, the UI must state that honestly rather than imply it is saved.

Persistence excludes repository archives, raw source bodies, provider response bodies, secrets, OAuth tokens, GitHub installation tokens, environment values and unsanitized model text.

## 17.3 Human review

Human review remains required for:

- authentication and persistence;
- migrations and retention;
- security and privacy claims;
- GitHub mutation;
- generated instructions affecting sensitive areas;
- workflow/CI targets;
- compliance-facing content;
- client-facing claims;
- new provider or model adapters.

## 18. Empty, limited and failure states

## 18.2 Limited scan

## 18.4 WebGL failure

- Automatically preserve the DOM pathway experience.
- No work or selection is lost.

## 18.5 Synthesis conflict

- The current draft remains visible.
- The highest-priority conflict and recovery are shown.
- The user may change goals or save a branch for later.

## 18.6 Apply failure

- Existing stage-aware recovery is reused.
- The product does not claim Applied to review branch or PR opened without provider evidence.
- ZIP/manual fallback remains available.

## 18.7 Incompatible verification

- Direct deltas and unlocks are suppressed.
- The incompatibility reason is shown.
- The next compatible rescan action is offered where possible.
